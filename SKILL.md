# Florida material risk: fast two-stage workflow

## Scope and non-negotiables
- Model: `PMGT - Inventory Planning V6.0`. Read Anaplan and the user-provided Excel BOM only. No writes, orders, processes or imports.
- First question (where are projected stockouts?): read inventory/shortfalls only. Follow-up (which finished goods?): read BOM, explode and join. Do not read BOM for stockout-only questions.
- Preserve explicitly established Florida DC, Scenario 1 and 26-week horizon in this conversation; otherwise use the user's location and horizon. With no location/horizon specified use **all locations and the full forecast horizon** and disclose that; do not silently substitute Florida or eight weeks. Ask for a scenario if multiple are available and none selected. Scenario is not the same thing as native Versions.
- On a refresh/re-run always read new numerical cells, but reuse already verified module schema, member names, BOM structure and selected scope while still valid. If model binding changes, rediscover. Prior reports are not evidence of present shortfalls.
- If Anaplan cannot be read, stop. If BOM is required but Excel sheet is not accessible, stop the finished-goods analysis and request it; a partial PDF excerpt or old answer is not the workbook.

## Fast path: minimum calls, in order

1. **Bind model only if unbound.** `get_model_context`; if needed `catalog_models` filtering the exact model, then `set_model_context`. Do not browse unrelated workspaces, skills or every module. For an unchanged model, keep previously verified identifiers; on a fresh session `catalog_modules(name_contains="IEO200")`, `catalog_line_items` for `Shortfall (U)` and forecast ending inventory/safety stock only if present, then one `sql_schema` for selected line items. Use exact returned dimension column names. If a read fails, `get_model_status` once to diagnose; do not repeatedly poll.
2. **SYS003 is the clock.** Call `list_time_anchors` once for relative time; identify the candidate **whose source/module is SYS003** (or the specific effective-current-period line item in SYS003), not merely the recommended native-calendar anchor. If SYS003 candidate is unread, follow its included_objects/next_action to read that single value; if absent, discover `SYS003` by name, find its effective current period line item, inspect `sql_schema` and read its cell with all dimensions fixed. Do not reuse an old SYS003 value as fresh. If SYS003 and native calendar disagree, the user has explicitly selected SYS003: `set_time_anchor(period=<verified SYS003 label>, source="custom_module", module=<verified SYS003 module>, line_item=<verified item>, confirmed_by_user=true)`. If two *SYS003* candidates disagree or its effective value cannot be read, ask the user which period is effective; never silently use `Week 1 FY25` or today's date. State that model weeks may be historical in real-world time.
3. **Get the exact horizon once.** Using the chosen module's time range and actual time scale, read the module's Time table in model order (`sql_schema` before any SQL table); take 26 consecutive weekly members beginning at the verified SYS003 period for “next 26 weeks”, inclusive. For unspecified horizon scan the full future forecast, not a default eight weeks. Do not invent week labels or calendar dates; if Time members/ordering are inaccessible, request an explicit period range. Confirm `Florida DC` and `Scenario 1` belong to their actual schema dimensions; pin native Versions to one explicit version if it exists. Never guess a list member from a previous report if membership fails now.
4. **Choose one of two read shapes; do not try both on every run.**
   - Small or sparse, and feasible to page: `read_cells` with location/scenario/native version sliced and product + time leaf, collect **all** pages, locally keep negative `Shortfall (U)`; include forecast inventory/safety stock when same module and dimensioned compatibly. Do not infer completeness from a first LIMIT page. Without a demonstrably bounded row count, use the per-week approach instead.
   - Large grid / likely timeout: one bounded `sql_query` per verified week, `included_objects` exactly one module (same map as `sql_schema`), slice time, location, scenario and native version to single members, leave **only product** as leaf. Apply `"Shortfall (U)" < 0` (negative means unmet demand); explicit LIMIT at tool's cap. If a week hits LIMIT, partition by verified product members or paginate with safe reads; mark incomplete if not exhausted. An all-week query filtered on shortfall with both product and time at leaf is **not allowed**. Never use `!=`, wide measure-filtered scans, unbounded cross-products, or `GROUP BY`/`DISTINCT` for a result that cannot be proven completely sliced.
   - Issue independent weekly reads in small parallel batches (e.g. 2–4), not 26 at once. On throttling, back off and resume only missing weeks. Keep a coverage ledger of weeks and pages; a zero is valid only when that week completed. On repeated timeout, stop and report verified subset and unscanned weeks instead of claiming a full scan or endlessly retrying.
   - Prefer forecast ending inventory by material/location/week for stockout detection when genuinely available; flag <0 and < safety stock if thresholds exist. `Shortfall (U)` is *unmet demand*, not ending inventory, safety stock or usable build stock. Label its negative observations accordingly. If only Shortfall is available, say inventory- and safety-stock-based risks are not assessed.
5. **Stockouts-only output:** list all confirmed material/location/first-at-risk-week and that week's value, plus coverage, selected SYS003 anchor, actual horizon and read date. Stop; do not search for BOM yet.

## Follow-up: finished-good impact
- Access every row of the supplied **Excel BOM** (not just a search excerpt); record finished good, component identity/Anaplan code, parent link, base and selected quantity, level and UOM. Join only exact confirmed identifiers (or verified SKU mappings), across **all** finished goods; list unmatched materials and exclude them. A BOM level alone does not prove a parent-to-child path. Where parent links exist, recursively multiply path quantities to leaf components and add duplicate paths; detect cycles. An optional component with base quantity zero only affects builds that select that option. Never assume every Synergy Frame includes a particular compute/storage blade.
- For each affected FG/location, find earliest flagged period and identify all same-week limiting components. `max buildable units = min(floor(max(0, usable component inventory)/configured quantity per FG))` over every required component. `unbuildable units = max(0, planned FG builds - max buildable units)` only when build plan and usable unallocated inventory exist. Negative Shortfall alone **cannot** determine either number or prove the capacity bottleneck: write `not determinable` rather than converting a material gap into FG units.
- Severity relative to SYS003 week: Critical weeks 1–4 or verified zero buildability; High weeks 5–8; Medium after week 8 or safety-stock-only breach. Optional-component risks are *conditional*, not confirmed mandatory FG risks. Count distinct FGs by highest confirmed severity; sort severity then earliest week.
- For each Critical/High FG: prioritize checks for transferable, uncommitted surplus and feasible transit; then open PO expedite, then new PO subject to verified supplier lead time; use a substitute **only** if approved. If supply cannot arrive in time, prioritize unaffected builds and flag possible delivery impact. If a component serves multiple FGs, ask planner for allocation priorities. State material, investigation quantity (round up fractional EA gap only as a provisional check), destination location and required model week/date for every specific action. Do not claim any donor surplus, order, delivery date or action has been verified or executed. A historical model week cannot be repaired by a new action today.

## Response template
One line: confirmed FG counts (Critical/High/Medium) and most urgent issue. Table: severity | finished good | constraining material(s) | location | first period | material shortfall/inventory vs safety stock | FG units unbuildable. Recommendations under each Critical/High FG; then optional/unmatched items, unavailable calculations, SYS003 period, all weeks actually scanned, forecast horizon, and date/time data was read. For stockouts-only output replace FG table with material table; never report prior numerical values as a new read.

## Quick checks (not live benchmarks)
- “I manage Florida; where are future projected stockouts?” → verify SYS003; read only Anaplan; no BOM.
- “Which finished goods are affected in Florida?” → read full Excel BOM; match codes across all FGs; no invented build capacity.
- “Refresh for 26 weeks” → verify SYS003 again; read fresh values in 26 actual consecutive model weeks; report partial coverage if a week times out.
